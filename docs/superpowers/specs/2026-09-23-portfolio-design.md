## 0. 목적과 성공 기준

**무엇**: 최하림(CHOI HALIM)의 취업용 개발자 포트폴리오 사이트입니다. 목표 직무는 **ML 엔지니어**이고, 신입(2028년 2월 졸업 예정)으로 지원합니다. 한국 회사와 일본 회사 모두 지원 대상입니다.

**누가 보나**: 채용 담당자와 현업 면접관.

**성공 기준**
1. 채용 담당자가 **30초~1분 안에** 세 가지를 파악할 수 있어야 합니다.
   - 누구인지
   - 무엇을 잘하는지
   - 대표 프로젝트가 무엇인지
2. 면접관은 대표 프로젝트 `airfare-forecasting-ml`의 문제, 검증, 한계를 사이트 안에서 따라가고, 코드까지 이어서 볼 수 있어야 합니다.
3. Awwwards/FWA 수준의 인터랙션을 갖춥니다. 다만 **연출이 정보를 가려서는 안 됩니다.** 움직임을 끈 환경에서도 모든 내용을 읽을 수 있어야 합니다.
4. 한국어, 영어, 일본어 3개 언어를 지원합니다.
5. **2027년 초까지 공개합니다.** 일본 新卒(2028년 4월 입사) 채용이 2027년 봄~여름에 몰리기 때문입니다.

**문구 원칙**: 슬로건이나 광고처럼 들리는 문장은 쓰지 않습니다. 꾸밈 없이 사실만 담백하게 씁니다.

## 1. 콘셉트

- **B. 가격 지형(Price Landscape)**
  - 실제로 수집한 항공권 데이터로 3D 지형을 만듭니다.
  - 축은 x=출발까지 남은 일수, z=출발일, 높이=가격(같은 편 평균 대비 %)입니다.

## 5. 3D 지형과 데이터 파이프라인

### 5.1 추출 스크립트 (`scripts/`)

모든 스크립트는 항공권 저장소의 `.venv/bin/python`으로 실행하고, 결과를 `public/data/`에 저장합니다. 사이트는 JSON만 읽기 때문에 빌드나 배포에 항공권 저장소가 필요 없습니다.

| 스크립트 | 입력 | 출력 |
|---|---|---|
| `export_terrain.py` | 원본 CSV + 항공권 저장소의 필터 함수(`src/processing/features.py`를 import해 재사용) | `terrain.<기준일>.json` |
| `export_demo.py` | `v2_predictor.pkl` + `recommend_action()` | `demo.<기준일>.json` |
| `export_facts.py` | 항공권 저장소 CLAUDE.md 기준 수치 | `data/facts.json` (빌드 시 import, 공개 URL 없음) |

- 항공권 저장소는 iCloud 안에 있습니다. 그래서 실행 전에 그쪽 CLAUDE.md의 **iCloud 워밍 절차**를 따릅니다. 모델을 돌릴 때는 NeuralProphet 로그를 억제합니다(`redirect_stdout`).
- 각 스크립트는 저장하기 전에 **출력 구조와 용량을 스스로 검사**합니다. 목표 용량을 넘으면 실패로 끝납니다.
- 파일 이름에 기준일을 붙입니다. 사이트는 `facts.json`의 `dataVersion` 필드로 실제 파일 이름을 찾습니다.

### 5.2 지형 데이터 (`terrain.json`) — 2026-09-23 실제 데이터 확인 후 수정

- 격자는 출발까지 일수(0~147) × 출발일(180개)입니다. 수집 기간이 5개월이라 데이터는 사각형이 아니라 **대각선 띠**입니다(가까운 출발일만 모든 예약 시점이 있음). 실제 칸은 2,070개입니다.
- **높이는 노선·등급 평균 대비 %** 입니다. 처음 스펙은 "같은 편 평균 대비 %"였지만, 그 방식은 출발일 효과(−37%~+63%)까지 지워 공휴일 봉우리가 사라집니다. 노선·등급 평균으로 나누면 노선별 가격대 차이는 없어지고 U자 골짜기와 공휴일 봉우리가 둘 다 보입니다(사용자 승인).
- **두 겹으로 그립니다 (신호 + 잡음, 사용자 승인)**
  - 신호: 칸(예약 시점 × 출발일) 평균 약 2,070개 → 밝은 점
  - 잡음: 칸 × 노선 × 등급 평균 약 24,500개 → 흐린 점. 표시 범위를 넘는 값은 잘라서 저장합니다.
  - 첫 화면에서 흐린 점이 흩어져 있다가 신호가 떠오르는 연출이 SIGNAL / NOISE와 맞닿습니다.
- 각 점에 **공휴일 주변 여부**(한·일 공휴일 ±3일)를 붙입니다. 호박색으로 그립니다.
- **빈 칸은 보간하지 않습니다.** 모든 점은 실제 평균값입니다.
- 직항 타당성 필터로 걸러진 **9,387행**은 별도 레이어(칸 약 1,600개)로 둡니다. 높이는 같은 노선·등급의 정상 평균 대비 %라 높이 떠 있다가, 3-3 챕터에서 떨어져 나갑니다.
- **예약 곡선 레이어(curve, 3-2 챕터 전용)**: 항공권 저장소 `realized_wait_analysis.py`와 같은 방법(이미 출발한 편, 편×수집일 최저가, 편 평균 대비 로그 가격, 출발까지 1~90일)으로 구한 날짜별 평균입니다. 8개 구간 평균이 본문 수치와 일치하는지 테스트로 확인합니다. 먼 구간은 주 1회 수집이라 날마다 표본 수가 크게 다르므로(41~13,392건) **점의 진하기·크기를 표본 수에 비례**시켜, 데이터를 빼지 않고 불확실한 날을 흐리게 보여 줍니다(2026-09-24 사용자 결정).
- 형식은 열 방향 배열로 저장하고 정수로 양자화합니다(%×10).
- 목표 용량은 **gzip 기준 300KB 이하**입니다.

### 5.2.1 지도 장면 (`map.json`, 사용자 승인)

- 3-1 "문제와 데이터" 챕터에서 점들이 **한국·일본 해안선** 모양을 이루고, 인천에서 나리타·하네다·간사이로 **노선 궤적**이 그려집니다. 3-2로 넘어가면 같은 점들이 흘러가 가격 지형으로 접힙니다.
- 해안선은 Natural Earth 50m(공공 도메인)에서 한·일 범위만 잘라 고른 간격으로 다시 샘플링합니다.
- 지도는 데이터 축이 아니라 "이 노선에서 모은 데이터"라는 맥락을 보여 주는 장면입니다. 지형의 축(예약 시점 × 출발일 × 가격)은 바꾸지 않습니다.

### 5.3 사이트 3D 구조

**설계 (계획 3 실행 완료 2026-09-24)**

- 화면 뒤에 고정된 캔버스 하나를 둡니다. 스크롤 위치에 따라 카메라가 챕터별 지점으로 이동합니다.
- 점은 `Points` 하나로 그립니다. 흩어지기, 모이기, 떨어져 나가기는 셰이더에서 계산합니다.
- 카메라 지점은 **가로 화면용과 세로(모바일) 화면용을 따로** 정의합니다. 세로 화면에서 텍스트는 지형 위에 겹치지 않고 하단 카드로 올라옵니다.

**구현 결과**

`src/three/` 모듈 (data.ts, scenes.ts, activeScene.ts, capability.ts, shaders.ts, TerrainPoints.tsx, CameraRig.tsx, TerrainScene.tsx)과 `src/components/Backdrop.tsx`, `src/sections/ChapterFigure.tsx`로 구성. 3D는 첫 화면 텍스트가 뜬 뒤 지연 로딩되며, `<html data-3d="on|off">` 속성으로 접근성 대체 처리(reduced-motion / WebGL 미지원 / 저사양 / 프레임 저하)를 이루어낸다. 네 개 장면: 신호가 잡음에서 떠오르는 첫 화면 / 한·일 해안선 + 노선 궤적(3-1) / 측면 U자 곡선 + 실측 예약 곡선 시각화(3-2) / 제거된 점 계층이 떨어져 내려오는 연출(3-3). 재학습 후: `npm run facts` → `npm run terrain` → `npm run build` → `npm run fallbacks` 순서로 데이터 갱신 및 대체 WebP 이미지 캡처 후 커밋.

## 6. 인터랙티브 데모 (섹션 4)

### 6.1 화면 (B1 레이아웃)

시안: `.superpowers/brainstorm/14017-*/content/demo-layout-v2.html` (B1)

- **질문 문장이 곧 선택 UI**입니다.
  - 한국어: "〔인천 → 나리타〕 가는 〔LCC〕를 〔11월 14일(토)〕에 타려면, 지금 살까요?"
  - 노선: 밑줄을 누르면 6개 노선 목록이 열립니다(ICN↔NRT, ICN↔KIX, ICN↔HND 양방향).
  - 등급: 누르면 LCC와 FSC가 번갈아 바뀝니다.
  - 날짜: 문장 아래 막대에서 고릅니다. 고른 날짜는 문장 안에서 호박색 밑줄로 표시됩니다.
  - 문장 틀은 언어마다 따로 둡니다. 일본어 예: 「〔仁川→成田〕の〔LCC〕で〔11月14日(土)〕に出発するなら、今買うべき?」
- **출발일 막대 = 날짜 선택기**
  - 막대 하나가 출발일 하나입니다(D+3~D+90, 88개).
  - 높이는 기준일(2026-09-22)에 샀을 때의 예측가입니다.
  - 공휴일 주변 출발일은 호박색으로 칠하고, 작은 표식과 이름표도 붙입니다.
  - 누르거나 끌어서 고릅니다. 키보드는 ←/→로 하루씩, Home/End로 처음과 끝으로 이동합니다.
- **결과**
  1. 예측가(플립 글자판)
  2. 80% 예측 구간 띠(q10~q90)와 양 끝 금액
  3. 추천 배지: `BUY NOW` / `DROP EXPECTED` / `WAIT`. 배지에는 항상 글자를 함께 씁니다.
  4. 이유 1~2줄. 확신도(높음/보통/낮음)는 `WAIT`, `DROP EXPECTED`일 때만 보여 줍니다.
- **"미리 계산된 예측 · 2026-09-22 기준"** 을 항상 표기합니다. 문장의 "지금"은 "기준일에 샀다면"이라는 뜻입니다.
- **처음 열었을 때 선택된 값**은 `DROP_EXPECTED`가 나오는 조합으로 둡니다. 전체 추천의 92.1%가 "지금 구매"라서 아무 조합이나 보여 주면 심심하기 때문입니다. 이 조합은 `facts.json`의 `demoDefault`에서 지정합니다.

### 6.2 데이터 (`demo.json`)

- 기준일은 2026-09-22입니다. 조합은 6개 노선 × 등급(LCC/FSC) × 출발일 D+3~90(모델 `MAX_DTD = 90`)입니다.
- 조합마다 다음 값을 저장합니다.
  - 예측가, q10, q90
  - 추천 `action`
  - **이유 코드와 값**
- 이유는 **문장이 아니라 코드와 값**으로 저장합니다. `recommend_action()`은 한국어 문장을 돌려주지만, 사이트는 3개 언어로 보여 줘야 하기 때문입니다. 문장은 사이트가 언어별 틀로 조립합니다.
  - 예: `{"action":"DROP_EXPECTED","bestDay":30,"bestPrice":171000,"savingPct":-8.7,"confidence":"medium"}`
- 대표 편은 최근 3주 동안 관측이 50건 이상인 편 중에서 고릅니다. 항공권 저장소의 시뮬레이션 기준과 같습니다. 대표 편이 없는 조합은 `null`로 둡니다.
- 공휴일 이름은 코드로 저장합니다(예: `hangul_day`). 이름표는 언어별 문구 파일에서 가져옵니다.
- 목표 용량은 **gzip 500KB 이하**입니다. 넘으면 출발일을 주 단위로 줄입니다.

### 6.3 데이터 접근 계층

화면 코드는 `ForecastSource` 인터페이스만 부릅니다.

```ts
interface ForecastSource {
  meta(): Promise<{ asOf: string; precomputed: boolean }>;
  getStrip(route: Route, cabin: Cabin): Promise<StripDay[]>;          // 막대용: 출발일, 예측가|null, 공휴일 코드
  getForecast(route: Route, cabin: Cabin, departDate: string): Promise<Forecast | null>;
}
```

- 지금은 `demo.json`을 읽는 `StaticForecastSource`만 만듭니다.
- 나중에 모델 서버가 생기면 `ApiForecastSource`를 추가하고 교체합니다. 화면 코드는 바뀌지 않습니다.
- "미리 계산된 예측 · … 기준" 표기는 `meta()`의 값으로 만듭니다.

### 6.4 문제가 생겼을 때

- `demo.json`을 불러오지 못하면 "데모 데이터를 불러오지 못했습니다"와 다시 시도 버튼을 보여 줍니다(3개 언어).
- 예측이 없는 날짜(`null`)는 막대를 회색 점선으로 그리고, 고를 수 없게 합니다. 키보드로 이동할 때도 건너뜁니다.

## 7. 다국어 (ko · en · ja)

- **주소**
  - `/`: 한국어(기본)
  - `/en`: 영어
  - `/ja`: 일본어

  언어마다 root layout을 따로 둡니다(route group). 그래서 정적 HTML에 올바른 `<html lang>`이 들어갑니다.
- **전환**
  - 상단 `KO · EN · JA` 버튼으로 바꿉니다. 선택한 언어는 `localStorage`에 기억합니다.
  - 처음 방문했을 때 브라우저 언어가 페이지 언어와 다르면 작은 안내만 띄웁니다(예: "日本語で見る →").
  - **자동으로 다른 주소로 넘기지 않습니다.** 받은 링크 그대로를 보여 주기 위해서입니다.
- **검색·공유**: 언어별로 `hreflang`, 제목과 설명, 링크 미리보기(OG) 이미지를 따로 둡니다.
- **문구 파일**
  - 문장은 `content/{ko,en,ja}.json`에 둡니다. **수치는 `facts.json`에만** 둡니다.
  - 문장 안의 수치는 `{r2_tss}` 같은 자리표시로 넣습니다.
- **글꼴**: Noto Sans JP는 일본어 페이지에서만 조각 단위로 불러옵니다. 한국어·영어 페이지에서는 불러오지 않습니다. `GATE 01 — PROBLEM` 같은 영어 연출 글자는 세 언어 공통입니다.
- **작업 순서**
  1. Claude가 한국어 초안을 씁니다.
  2. 사용자가 한국어를 검토합니다.
  3. Claude가 영어·일본어 초안을 만듭니다.
  4. 영어는 사용자가 검토하고, 일본어는 사용자가 섭외한 검수자가 확인합니다.

## 8. 성능

### 8.1 로딩 순서

1. 첫 화면 텍스트(이름, `ML ENGINEER`, 키워드)는 **정적 HTML에 포함**합니다. JS 없이도 바로 보입니다.
2. 로딩 화면은 **최대 1.2초의 고정 연출**입니다. 실제 로딩 진행률과는 연결하지 않습니다. 같은 세션에서 다시 들어오면 건너뜁니다(`sessionStorage`).
3. 텍스트가 뜬 다음 3D 코드 묶음과 `terrain.json`을 **지연 로딩**합니다. 준비되면 점이 모여드는 연출로 등장합니다.
4. `demo.json`은 데모 섹션에 가까워지면 불러옵니다(IntersectionObserver).

### 8.2 목표 수치

| 항목 | 목표 |
|---|---|
| LCP | 중급 휴대폰 4G에서 2.5초 이하 |
| 초기 JS (3D 제외) | gzip 150KB 이하 |
| 3D 코드 묶음 | gzip 약 250KB |
| `terrain.json` / `demo.json` | gzip 300KB / 500KB 이하 |
| CLS | 0.1 미만 |
| 프레임 | 데스크톱 60fps, 모바일 30fps 이상 |
| Lighthouse 성능 | 모바일 90 이상 |

### 8.3 기기에 맞춘 조절

- 모바일에서는 점 개수를 절반으로 줄이고, 화면 해상도 배율(DPR)을 최대 1.5로 제한합니다.
- 30fps 미만이 2초 넘게 이어지면 점 개수와 DPR을 한 단계 낮춥니다. 그래도 느리면 정적 이미지로 바꿉니다(§9.1).
- 탭이 숨겨졌거나 캔버스가 화면 밖에 있으면 렌더를 멈춥니다.

### 8.4 캐시

- 데이터 JSON은 파일 이름에 기준일이 들어 있으므로 오래 캐시합니다(`immutable`).
- `facts.json`은 짧게 캐시합니다.

## 9. 접근성

### 9.1 대체 화면

- 아래 **넷 중 하나라도** 해당하면 3D 대신 대체 화면을 씁니다.
  - `prefers-reduced-motion`
  - WebGL을 쓸 수 없음
  - 저사양 기기(`deviceMemory ≤ 2`)
  - §8.3의 지속적인 프레임 저하
- 대체 화면에서는 **챕터별 정적 WebP 이미지**를 보여 줍니다(첫 화면, 3-2, 3-3, 3-5 등).
  - 이미지는 실제 3D 장면을 **캡처 스크립트**(Playwright)로 찍어 커밋합니다.
  - 이미지마다 대체 텍스트를 붙입니다.
- 플립 글자판은 최종 값만 보여 주고, 텍스트 리빌과 Lenis는 끕니다.
- 콘텐츠와 데모는 **전부 그대로 동작**해야 합니다.

### 9.2 키보드

- 맨 앞에 "본문으로 건너뛰기" 링크를 둡니다.
- 모든 조작 요소는 Tab으로 갈 수 있습니다. 포커스 테두리는 호박색으로 또렷하게 보여 줍니다.
- 데모의 출발일 막대는 `role="slider"`로 만듭니다(§6.1의 키 조작).

### 9.3 스크린리더

- 3D 캔버스는 `aria-hidden` 처리합니다. 모든 내용은 실제 텍스트로 존재합니다.
- 플립 글자판은 글자 조각을 숨기고 완성된 값을 `aria-label`로 제공합니다.
- 막대의 `aria-valuetext` 예: "11월 14일 토요일, 예측가 187,400원, 공휴일 주변".
- 데모 결과가 바뀌면 `aria-live="polite"`로 **조작이 멈춘 뒤 한 번만** 알립니다(디바운스).

### 9.4 색 대비

- 본문은 WCAG AA(4.5:1 이상)를 지킵니다. 흐린 보조 글자도 이 기준 아래로 내리지 않습니다.
- 색 하나에만 의미를 맡기지 않습니다. 공휴일에는 표식과 이름표를, 추천에는 글자 배지를 함께 씁니다.
